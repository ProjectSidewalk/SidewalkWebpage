# Translations

Full rules: `docs/internationalization.md`.

- **Backend English goes in `conf/messages/messages.en`, never the base `messages`** (that is the language-neutral
  fallback for city names and way-type keys). Every `messages.<lang>` carries every key; the non-English languages
  fall back to the base file, not to `messages.en`, so a missing key renders raw. There is no parity check for the
  backend files.
- **Escape a literal apostrophe as `''`** in message files: `MessageFormat` silently drops a lone `'`.
- **Frontend keys go in every full locale** (`en`, `es`, `nl`, `de`, `pt-BR`, `zh-TW`, `fr`); `make lint-locales`
  enforces parity. `en-US`, `en-NZ`, and the per-city overlays hold only the keys that differ.
- Machine translations are fine for the first pass; add them in the same PR rather than blocking on partners.
- Unit words live only in `conf/messages` (`unit.distance.*`); locale JSON never carries imperial wording, and
  `en-US` is a spelling overlay, not a units overlay.
- **i18next interpolates values verbatim** (`escapeValue: false`, set in `AppManager._setupI18next`), because most
  land in a text node or an `aria-label`. A `t()` call whose result builds HTML must escape them — `interpolation:
  { escapeValue: true }`, or `util.escapeHTML` at the sink — and the `ps/i18n-escape-in-markup` ESLint rule blocks
  the ones it can see. `{{- var}}` in a locale string is raw whatever the setting is.
